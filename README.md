# Isildur

Isildur is the company. **ASE** is its product: an ontology powered data intelligence
platform. This repository is the working prototype: a Python/DuckDB backend that ingests
messy, fragmented source systems and resolves them into one queryable knowledge graph, and
a Next.js frontend that presents it as a landing page, a gated onboarding flow, and an
authenticated app (graph, search, dashboard, Control Room, demo workspace).

Everything here runs locally. No cloud, no real accounts, no external services. All sample
data is synthetic — either generated by the backend pipeline or built in the browser from
fixtures.

## Repository layout

```
isildur/
  backend/            Python + DuckDB + FastAPI — data pipeline and read-only API
  frontend/           Next.js 16 App Router + Tailwind — marketing site and app
  docs/isildur.md     Product requirements document / prototype audit
```

## Architecture, at a glance

The backend is organized around a clear separation between the **domain model**, the
**pipeline** that produces instances of it, and the **API** that serves it:

```
backend/
  ontology.py         domain schema — object types and relationship types (Part B)
  sources.py          provenance manifest for the vendor source systems
  pipeline/           the ETL pipeline, run in order:
    generate_data.py      1. synthesize messy multi-format source systems
    ingest_clean.py       2. ingest + normalize (field mapping, currency, timezone, status vocab)
    entity_resolution.py  3. resolve records into canonical objects + typed links
    findings.py           4. compute operational findings across sources
  app/                domain-driven FastAPI surface over the resolved graph
```

The frontend is a Next.js App Router project. Routing lives in `app/`; everything else is
sliced by feature rather than by technical layer:

```
frontend/
  app/                    App Router — routing, layouts, loading/error boundaries only
    (app)/                route group for gated surfaces: /app/* and /demo/*
      layout.tsx            the authenticated app shell (sidebar + topbar)
      app/graph|search|dashboard|graph-next|control-room/
      demo/enter|workspace/
    page.tsx              ungated marketing routes live outside the group:
    about|contact|documentation|how-it-works|request-access/
  features/<name>/        components, hooks, services, stores, schemas, types
    marketing, access, app-shell, graph, search, dashboard,
    graph-next, control-room, ase, demo, findings
  components/ui/          shadcn primitives
  lib/                    axios client, access-cookie helpers, query client, cn
  middleware.ts           access gate for /app/* and /demo/*
```

### Three demonstration domains

Worth knowing before reading the code — the prototype tells three unrelated stories, and
only one of them touches the backend:

| Surface | Data source |
|---|---|
| `/app/graph`, `/app/search` | **Backend.** The synthetic online gaming operator, via the DuckDB-backed REST API. |
| `/request-access` | **Backend.** `POST /access-requests`. |
| `/app/control-room/*`, `/app/graph-next`, `/app/dashboard`, `/demo/*` | **Browser only.** An expedition-safety world generated client-side from fixtures. The API is never called. |
| `/app/control-room/findings` | **Browser only.** A leftover "Argent Holdings" payments mock. |

`docs/isildur.md` §15.1 covers why this split exists and what it costs.

## Running it locally

**Backend**

```bash
cd backend
python3 -m venv venv && venv/bin/pip install -r requirements.txt
venv/bin/python pipeline/generate_data.py
venv/bin/python pipeline/ingest_clean.py
venv/bin/python pipeline/entity_resolution.py
venv/bin/python pipeline/findings.py
venv/bin/uvicorn app.main:app --port 8010
```

The four pipeline stages must run in order and only need re-running when you want fresh
data — `isildur.duckdb` and `data/raw/*` are gitignored build artifacts. Check it is up
with `curl -s localhost:8010/health`.

**Frontend**

```bash
cd frontend
npm install
npm run dev
```

Then open <http://localhost:3000>.

Available scripts: `dev`, `build`, `start`, `lint`, `format`, `typecheck`, `test`.

**Configuration**

Copy `frontend/.env.example` to `.env.local` to change anything. The only
variable read today is:

| Variable | Read by | Default |
|---|---|---|
| `NEXT_PUBLIC_API_URL` | `lib/axios.ts`, in the browser | `http://localhost:8010` |

Data fetching is currently client-side, so the browser talks to FastAPI directly and the
default works with no `.env.local` at all. A server-side `API_URL` (for an `app/api/`
Route Handler BFF) is planned but not yet wired up — nothing reads it on `main`.

The old Vite `VITE_API_URL` variable is gone; it does nothing.

## Checks

```bash
cd frontend
npm run typecheck && npm run lint && npm test && npm run build
```

`npm test` runs Vitest over `features/{ase,graph-next,control-room}` — the pure
service/store logic behind the Control Room and Graph Next. There is no test suite for the
FastAPI layer.
